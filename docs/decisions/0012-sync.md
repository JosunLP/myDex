# 0012 – Optional sync

Status: accepted; encryption added by ADR 0014

## Context
Personal data should optionally sync between devices without the app requiring an account or a
network (ADR 0002, 0003) and without endangering GrapheneOS acceptance (no unnecessary
permissions).

## Decision
- **Self-hosted server** (`tools/sync_server`): one Dart process with SQLite. Accounts get a
  random access token (256 bits), stored only as a SHA-256 hash. No password, no email, no
  provider account.
- **Scope:** collection, teams, filter presets. Not synced: settings (device-specific) and the
  catalog (reproducible). Server address and token are stored separately from the settings and
  never end up in a backup.
- **Protocol** (`packages/sync`, version 1): a single `POST /v1/sync` call sends the outbox and
  fetches other devices' changes since its own cursor (paged, at most 500 per page).
  - Every accepted change gets an account-wide increasing revision.
  - Optimistic concurrency: a change carries the last known revision; if it differs, the server
    answers with a conflict and the current state instead of overwriting.
  - Deletions are kept as tombstones. “Delete data on the server” removes all records, but
    revisions never go backwards.
- **Outbox:** local changes are coalesced per record, survive restarts and are sent a few
  seconds after the last change, at startup and on demand. Without a network everything stays
  usable locally.
- **Conflicts:**
  - Collection entries: the newer state wins (per entry).
  - Teams and filter presets: if both sides changed, the server version stays under the ID and
    the local one becomes a copy with the suffix “(conflict)”. Edits win over deletions. An edit
    is never lost silently.
- **Transport:** HTTPS; plain HTTP only to local addresses (own machine, Android emulator). TLS is
  handled by a reverse proxy in front of the server.
- **No end-to-end encryption** in version 1, as planned in the architecture draft (added later by
  ADR 0014 without a protocol change; the server treats `data` as opaque).
- **Android flavors:** `offline` (default) without internet permission and without sync; `sync`
  with internet permission and its own package ID (`….sync`). All other platforms offer sync
  optionally; macOS gets the sandbox entitlement `network.client` for it.

## Consequences
- Whoever wants sync needs their own server or a trusted operator.
- Android builds need `--flavor offline` or `--flavor sync`.
- Tombstones grow over time; for the expected amount of data (hundreds to a few thousand
  entries) this is not an issue. Pruning old tombstones can be added later.
